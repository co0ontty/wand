## 确认属于历史堆积、应由系统考虑自动处理

1. **重复/过旧的客户端构建包**：同目录里存在跨多个版本、同版本多次构建的 IPA/DMG/ZIP，能累积到数 GB。系统已对 Android APK 有 `DistributionManager.pruneAndroidApkDirectory()`，而 iOS/macOS 历史构建没有对应的同等保留清理。建议在成功部署新包后，按平台和更新通道保留当前发布、配置 pin 的包及少量回滚包，删除较旧同类产物；macOS 需一并处理 sidecar，且绝不删正在传输的文件。
2. **迁移前 SQLite 快照无保留上限**：`wand.db.pre-vN-*.bak` 会随 schema 迁移增长，旧快照体积很大。本机发现多个早期迁移备份和一份 7 月旧快照。建议迁移成功且数据库健康检查通过后执行有界保留（例如保留最近数个迁移点或按天数/空间上限），迁移失败则绝不删回滚文件；须提供 dry-run、日志和可配置保留策略。
3. **临时 QA/探测产物**：探测截图、临时 note 和已结束的空验收目录没有长期运行价值。建议统一写入带任务/创建时间的临时目录，任务结束或达到 TTL 后回收；避免通过宽泛文件名模式删除用户内容。
4. **配置备份**：带日期的 config snapshot 若无限保留会积累且容易产生误选。建议仅保留最近少量恢复点，写入新配置并校验成功后再清旧备份，权限继续限制为用户私有。

## 不应自动当垃圾清理

- `wand.db`、`sessions/`、`pi-native/`、`taskboard/`：是应用状态/历史数据，清理需要独立的数据保留与用户确认机制。
- `local-models/`、`speech/`：可能是昂贵或耗时下载的模型/运行时；应由模型/运行时清单确认未使用后才可回收。
- `acceptance-connection.json`、`config.json`、`wand-vault.key`、证书/私钥及 token：配置或凭证。不能按“旧文件”自动删除，也不得把内容写入清理日志。
- PID、socket、token、活动日志：运行时正在使用；应通过服务生命周期和安全轮转管理，禁止仅按文件名清除。当前 `web.log` / `web-error.log` 由运行中的服务使用，本轮未触碰。
- `backups/` 中的任务部署/归档数据库快照：名字表明其对应恢复点，本轮未验证可丢弃条件，故保留。

## 开发者实施建议

- 将平台产物清理统一放在分发/部署生命周期中，而不是定时无差别扫描。清理前计算候选、校验配置 pin 与下载流引用、限制在配置的分发目录内；删除失败不影响发布或下载。
- 发布流程先写临时文件、验证 SHA/大小/元数据、原子切换当前版本，最后才按保留规则 prune。更新 API 选择逻辑与清理策略必须共享版本比较器，避免删掉仍会被选中的候选。
- 数据库备份用单独、可审计的策略：迁移成功/健康检查通过才 prune；至少保留最近 N 个迁移前快照、最近 T 天快照和一个已知健康快照，并设最大空间提醒。不能违反“schema 迁移只加不删”的项目约定。
- 日志采用按大小/日期轮转、压缩及期限保留；不要 unlink 正被进程打开的文件。提供受控的维护命令输出候选清单、数量与预计释放空间。
- 清理器需有 dry-run、可观测结果（不含秘密）、幂等性、路径防穿越检查、测试覆盖 pin/当前下载/失败发布/权限错误/磁盘空间边界。清理策略变化写入 `docs/storage-cleanup.md` 并补对应测试。
