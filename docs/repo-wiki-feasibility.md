# Repo Wiki 接入知识库的可行性与成本

状态：调研结论，未实施。2026-10-30。

## 结论

可以接，而且应该接在**项目知识库**里，作为与手工约定并列的一类文档，而不是塞进全局库。

三条边界决定了形态：

1. **Wiki 是参考资料，不是规则。** 全局库每轮完整注入、按约定执行；Wiki 是生成内容，会随代码漂移，只能作为“先看这里”的索引，关键结论仍要回源码核对。
2. **不能整包注入。** 本仓主仓约 1126 个文本文件、10.4 MiB（≈280 万 token）；加上四个子模块共约 1835 个文本文件、29.6 MiB（≈570 万 token）。Wiki 全量几十页、上百 KB，必须“目录 + 摘要进上下文，正文按需读”。
3. **生成与消费分离。** 生成交给已有工具（Qoder Repo Wiki 或开源 repowiki），Wand 只负责导入、存储、检索、引用和新鲜度提示。自己写生成器是成本最高、收益最不确定的一条路。

## 外部实现对比

| 方案 | 形态 | 成本/依赖 | 增量更新 | 导出 | 许可 |
| --- | --- | --- | --- | --- | --- |
| Qoder Repo Wiki | `qoder wiki`，官方托管 | 需登录+联网；固定模型，约 50 Credits/仓库（全量），更新另计 | 有（Auto Update，按提交增量） | `.qoder/repowiki/{zh,en}/` Markdown + `knowledge/` 卡片 | 商业 |
| repowiki | `pip install repowiki`，本地 CLI | Python + 自备模型 API Key；无 Docker | 有（`.repowiki-state.json` + SQLite 内容缓存，未变页面不调模型） | Markdown / JSON / HTML | MIT |
| deepwiki-by-cc | Bun + Claude/Codex CLI，Docker ~850MB | 需已登录 CLI | 有（按 diff 重写受影响页） | SQLite + Web | MIT |
| deepwiki-open | Docker + PostgreSQL + 向量库 | 依赖最重 | 较弱 | Web | MIT |
| 自研（用 Wand 会话生成） | 复用现有 structured 执行 | 无新依赖，但需自建扫描、大纲、分页、增量状态、引用校验 | 需自建 | 自有 | — |

Qoder 官方限制：仅 Git 仓库且至少一次提交、单仓库最多 10,000 文件；生成与更新都消耗 Credits；Wiki 与知识卡片是两套内容。引用（Citation）目前只在 Qoder 自己的任务里生效，其他 CLI 拿不到，这正是 Wand 需要自己补的一层。

## 与现有实现的差距

现有知识库（全局/个人/项目）已经具备：稳定归属、版本号与冲突保护、能力令牌与失效、200 篇/12,000 字符上限、项目库 4KB 目录 + 6KB 正文预算、四端同一套“目录 + 正文”界面。接入 Wiki 需要补的只有五点：

1. **文档来源标记。** 现在每篇文档只有标题、目录、正文、版本。需要区分“手写约定”和“生成 Wiki”，并记录仓库路径、分支、生成提交、生成器、语言、生成时间。
2. **层级目录。** 现在目录是单层字符串（`folder`），Wiki 是树。最小改法是把目录当成 `架构/核心模块` 这样的路径来解析并渲染成多层树，不改表结构。
3. **单篇上限与凭据处理。** 12,000 字符对多数页面够用，但架构总览类页面会超；且现有凭据检查是“命中即拒收”，而 Wiki 正文里出现 `apiKey: "..."` 这类代码示例是正常的。导入路径需要改成“扫描并脱敏 + 记录脱敏位置”，而不是整篇拒绝。
4. **源码引用跳转。** Wiki 的 `path#L120-L140` 需要能打开文件并定位行区间。当前文件预览只支持 `path:line` 的读取回退，没有行区间滚动与高亮。
5. **新鲜度。** 必须显示“基于哪个提交生成”“当前 HEAD 是否已变化”。没有这个，模型会把过期文档当现状。

不需要改的：权限模型、四端页面骨架、Markdown 渲染、草稿与冲突逻辑、全局 24KB 预算（Wiki 不进全局）。

## 呈现与使用逻辑（建议）

**呈现**：项目知识库左侧仍是一棵树，根节点分为「约定」（手写）和「代码 Wiki」（生成）。Wiki 页顶部固定一行元信息：生成器、分支、提交短哈希、生成时间、语言；HEAD 变化时这行变成“已过期，建议更新”，并给出更新入口。正文右上角保留“在源码中打开”的引用列表。

**使用**：

- 进入绑定了项目的会话时，项目库只注入 **Wiki 目录 + 每页一句摘要 + 生成提交**（约 3–4 KB，独立预算，不挤占手写约定），并明确标注“这是生成索引，正文需按需读取”。
- 模型判断相关时调用 `knowledge:read <id>` 读整页；搜索走 `knowledge:search`，先做子串匹配，页面数超过阈值再上 SQLite FTS5。
- 页内 `path#Lx-Ly` 通过项目 cwd 解析，点击直接跳到源码行区间；引用打不开时明确报错，不回退成“猜一个文件”。
- 全局库、个人库不引入 Wiki。跨项目通用结论由用户显式“记住到全局”，不从 Wiki 自动提升。

**更新**：不建常驻守护进程。提交后由用户点“更新”，或在会话里让模型跑一次生成命令；导入按“页面路径 + 生成提交”去重，页面删除时同步删除对应文档，但保留用户手改过的页面并标注冲突（与现有 revision 冲突语义一致）。

## 成本估算

以本仓 5 个仓库（主仓 + android/ios/macos/render）为口径，单人估算，含验证：

| 阶段 | 内容 | 工作量 |
| --- | --- | --- |
| P1 导入与浏览 | 来源字段 + 迁移、目录路径树、导入命令、四端来源徽标与过期提示 | 6–8 人日 |
| P2 检索与注入 | Wiki 独立索引预算、按需读取、搜索、四端引用跳转 | 4–6 人日 |
| P3 生成接入（二选一） | A：包 `qoder wiki`（登录/额度/状态 UI）约 2–3 人日；B：包 repowiki（Python 运行时与 Key 管理）约 3–4 人日 | 2–4 人日 |
| P4 行区间引用 | 文件预览支持 `#Lx-Ly` 定位与高亮，Web/macOS/Android/iOS 各端 | 4–6 人日 |
| 自研生成器（不建议先做） | 扫描、大纲、分页、增量状态、引用校验 | 10–15 人日 |

一次性生成成本：Qoder 约 50 Credits/仓库，5 个仓库约 250 Credits；后续每次增量更新按改动范围计费。repowiki 走自备模型，按实际 token 计费，未变页面因内容缓存不产生调用。

## 主要风险

- **漂移**：Wiki 与代码不一致是常态。没有提交标记和过期提示，就等于给模型喂过期事实。
- **误当规则**：生成文本里会出现“应该”“必须”这类描述。若放进全局库并被当作约定执行，会把文档描述变成行为约束。必须留在项目库的“参考资料”类别。
- **体量与成本**：整包注入会挤掉真实上下文；按页读取则依赖检索质量，索引摘要写不好就找不到页面。
- **凭据误伤**：代码示例中的 key 形态会触发现有拒收规则，导入必须脱敏而不是丢弃整页。
- **多端一致性**：四端都要显示来源与过期状态，否则用户在不同端看到的事实不一致。

## 建议的落地顺序

先做 P1 + P2：用现成的 `qoder wiki` 或 `repowiki` 生成一次，导入项目库，验证“目录可浏览、索引可注入、页面可按需读取、引用可回源码”。这一步不引入新运行时，也不改变全局约定语义，能最快判断 Wiki 对实际任务是否有帮助。

确认有效后再做 P3 的生成接入和 P4 的行级引用。自研生成器留到前两步证明收益不足时再评估。
