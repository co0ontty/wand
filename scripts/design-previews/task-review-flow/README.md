## 参考结论与用户本轮新增要求

参考 `output/dashi-taskboard/skills/manage-taskboard/SKILL.md` 的 Core workflow 6–7，以及上游 README：

> 执行并验证、写证据后进入 in_review；只有用户明确接受才进入 done。

dashi 的 `in_review` 是**等人确认**，并不是“等 AI 开始验收”。不能机械把它翻译为“待验收”然后丢掉操作者语义。本轮在它的人工接受边界之前，明确增加 AI 验收关口。

| 阶段 | 谁做什么 | 进入条件 | 离开方式 |
| --- | --- | --- | --- |
| 待立项 | 人确认范围与是否执行 | 尚未授权开始 | 明确立项 → 等待认领 |
| 等待认领 | 选择执行对象 | 已明确范围 | 显式派发 → 执行中 |
| 执行中 | AI 执行或修复 | 工作开展 / 验收退回 | 明确提交交付与证据 → 待验收 |
| 待验收 | AI 核验范围、版本、结果与真实交互 | 交付已提交，不是会话刚结束 | 通过 → 待归档；不通过 / 无法验证 → 执行中，保留原因 |
| 待归档 | 人检查 AI 报告与实际体验 | AI 明确通过，证据齐全，无未验证项 | 确认并归档 → 已归档；人工退回 → 执行中 |
| 已归档 | 收纳已接受交付，保留记录 | 人工确认、运行事实允许归档 | 本轮不改变现有恢复/历史能力 |

“待归档”并不表示用户已经验收；卡片副文案是 **AI 已通过 · 等你确认**。主操作为 **确认并归档**，不是 AI 自动归档。若未来需要“只接受、稍后归档”，仍须保留接受与收纳两个事实，不能悄悄合并数据。

## 不能只做文案替换

当前生产事实（已阅读对应源码）：

- `src/task-types.ts` 只有 backlog / todo / doing / done / archived，无独立 AI 验收阶段。
- `task-board-agent.ts` 把 done 命名为“等待验收”；`TaskAcceptance` 的 acceptedAt 明确表示用户接受。
- `server-task-routes.ts` 通用 PATCH 可以写 acceptance，但没有 AI 验收型动作，写 acceptance 不驱动状态。不能把这个所有者接口直接发给员工。
- `task-archive-policy.ts` 主要检查 doing / 活跃会话 / 团队，不是 AI 通过与人工确认的完整门禁。`retention-protection.ts` 的自动归档另有 acceptedAt 限制，正式改造必须同时核对。
- TASK-184 的既有阻塞说明、TASK-185/188 的证据均表明“模型说验完”并不等于结论已落库。

### 正式落地边界

1. 独立记录 AI 验收与用户接受。AI 字段至少包含结论（通过 / 不通过 / 无法验证）、证据、缺口、验收对象版本、源任务/会话、操作者与时间；acceptedAt 继续只表示明确人工接受。原评论、证据和历次结论保留。
2. 用明确的“提交验收 / 写入 AI 结论 / 人工确认归档 / 退回”动作驱动状态，在 storage 原子边界内同时校验版本和写入结论。通用拖拽、下拉、PATCH、DELETE 归档、工作区归档、定时清理不能绕过门禁。
3. 员工写入只限当前明确派发且有授权的任务，必须有 requestId 幂等与 taskVersion 保护；无凭据、过期、跨任务、人工接受字段写入均拒绝。不扩大到同项目全部任务。重试未知回执先查结果，不重复派发。
4. 执行会话结束不自动提交；只有执行者显式提交目标与交付证据才进入待验收。换列不自动启动验收模型；启动仍走已有派发入口、候选与费用边界。验收未写入真实回执只显示“结论待回填”，不能靠正文关键词猜通过。
5. AI 通过必须对应当前交付 revision；返工、改变范围或交付后旧结论失效，迟到回填不得覆盖新一轮。验收失败回执行中不代表自动派发修复。主任务整体验收同时核对子任务所需验收，不按会话数算完成。
6. 人工确认与归档合并为一个 UI 动作，但服务端在同一原子入口记录人工接受与归档；仍检查真实执行、排队、团队屏障。失败保持原状态与草稿，不强停进程，不删除历史。
7. 旧 done、旧 acceptedAt 不自动证明 AI 已通过或是谁接受。未有可信来源的记录显示“历史验收待核对”，不能自动迁移为 AI/人工已通过。迁移方案先盘点并留审计，不批量改写历史；数据库只加不删。
8. Web/Mac、Android/iOS 均同步列名、筛选、列表/看板/甘特/统计、子任务汇总、行动入口、详情按钮及更新协议。源数据与状态机唯一，不另加 GET 全表修复。

### 验收矩阵（正式落地仍待执行）

- 正向：执行提交 → 待验收 → AI 通过 → 待归档 → 人工确认 → 已归档。
- 反向：AI 不通过、无法验证和人工退回均回执行中，缺口、证据、旧结论不丢。
- 禁止捷径：会话结束、已读、评论正文、拖列不能直接认定 AI 通过或人工接受。
- 边界：父子任务、活跃/排队执行、迟到结果、相同 requestId 重放、版本冲突、跨任务/过期员工授权、未知回执、旧客户端与旧任务。
- 四端各自验证；共享协议/存储跑 check/test/build；受影响流程最后使用已安装服务验收。预览测试不能替代生产验收。
